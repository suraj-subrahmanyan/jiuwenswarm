As-is RSI verdict. The candidate→policy-check→store→promote mechanics are implemented and unit-tested, and the governance properties (frozen sections, dry-run default, atomic promotion, rollback) are real code — but nothing produces trajectories for GEPA and nothing consumes its promotions. No RSI loop is executable end-to-end today, and no diagram or document should claim otherwise.

3.1 What v1 actually enforces (as-is)

The manifest is not decorative — three enforcement layers exist today, all in harness/lib/capability_capsules.py:

LayerChecksFailure behaviour
Schema validationDraft 2020-12 JSON Schema (schemas/draft/capability-capsule.v1.draft.json)error list from validate_capability_capsule
Semantic validation (:618-652)non-empty pre/postconditions and invariants; all four effect classes present; secret_refs ⇒ at least one guard.* reference; resource capsules may not declare effects.execute; guard capsules must declare pass conditionserror list; registration blocked
Resolution (:1246-1338)the seven checks of diagram LL-2 band B, each with a typed CapsuleResolutionError stringhonest stall — no silent degradation
The as-is status problem. The registry's single status field expresses definition maturity only. Nothing anywhere in the 42 manifests or 35 entries records whether a capsule has ever executed, is currently executable, or has independently verified evidence. "Stable" therefore reads as "works" while meaning only "schema settled" — the motivating defect for §4.

Axis independence (invariant). stable + unbound + unassessed is a legal, common combination. certified requires verified history but never implies runnable-now. A dashboard may summarise the three axes into one badge; the stored model never collapses them.

# Proposal — Capability Capsule v2, DRAFT 2
# (draft 1 revised per design-review/adversarial-review.md findings M-2..M-5)
#
# Design rule:
#   A Capsule is a governed, reusable capability blueprint created before a
#   project is planned. The Planner selects it and expands its ordered steps
#   into the project TaskGraph. Each step's typed action identity is a Logical
#   Operator; Skills are the primary reusable ingredients under it. MCP/tool
#   requirements are typed resources. Runtime executor selection is a later
#   concern and remains in the Physical Operator registry.
#
# Schema invariants (enforced by the JSON schema + semantic validator; these
# migrate from v1 — see capability_capsules.py validate_capability_capsule_semantics):
#   I1. resources.secret_refs non-empty  =>  composition.required_guard_capsules
#       non-empty (v1 rule retained across the bindings->resources relocation).
#   I2. capsule_kind == resource  =>  effects.execute empty.
#   I3. capsule_kind == guard     =>  verification declares pass conditions.
#   I4. No field anywhere may name a permanent agent/team/model instance;
#       pin_binding_for_attempt is the only sanctioned pinning.
#
# Migration rules (v1 corpus -> v2):
#   MG1. Registry default_operator_profile is DELETED from registry entries;
#        defaults move to the Physical Operator registry keyed by capability
#        (resolves the forbid_identity_pinning conflict, review M-4).
#   MG2. v1 runtime_preferences (6 manifests) maps into
#        executor_policy.model_requirements / permitted_operator_kinds.
#   MG3. Manifests without version (19 of 42) are backfilled 0.1.0 from the
#        registry entry's version at migration.
#   MG4. Kind-conditional sections: planning_blueprint is required for
#        capability/adapter, forbidden for resource, optional for guard.
#
# ID prefixes by kind: cap. | guard. | resource. | adapter.
